# 0006 Database storage and access boundaries for platform service credentials

Date: 2026-10-05. Status: **accepted.**

## Context

Platform operators need to maintain provider credentials in the `/app` platform console. At the time of this decision, [llm.py](../../server/app/providers/llm.py) mapped platform models' `credential` through `credential_value` to environment variables; search and standalone model adapters read keys from [Settings](../../server/app/core/config.py). Changing these values required deployment configuration, and API/worker processes could hold different values.

Org (organization/tenant, 单位) BYOK is already encrypted by [ProviderSecrets](../../server/app/core/provider_secrets.py) and bound to its org and configuration revision; see [provider-config.md](../notes/provider-config.md#revisions-and-authority). Platform service credentials belong to no org and must not be placed in an invented org to evade [agent.md hard rule 1](../../agent.md#hard-rules-must-never-be-violated). The global-table exceptions approved in [ADR 0001](0001-platform-console-access.md) and [ADR 0002](0002-prepaid-billing.md) do not automatically cover this proposal.

## Decision

The [platform credentials contract plan](../plan/platform-credentials.md) defines data structures, routes, migration steps, and acceptance.

- Approve one narrowly scoped global table, `platform_credentials`, without `org_id` or tenant RLS. It stores only platform-owned outbound service credentials plus encryption and administrative metadata. It must not store org BYOK, business content, login identities, platform administrator lists, or its own unlocking keys. Add no global plaintext/ciphertext credential-history table. Include this exception and its dedicated-role boundary in `agent.md` hard rule 1.
- Migrate `BID_PLATFORM_CREDENTIAL_<NAME>`, `BID_PERPLEXITY_API_KEY`, and `BID_LLM_API_KEY` into the database. The latter covers standalone/eval and cannot become an implicit fallback model for org jobs. Org BYOK keeps its tenant tables and permissions. Confirm capability contracts before adding cloud OCR, Embedding, or other providers; do not expand this table into an arbitrary key/value configuration center.
- Startup, trust roots, and infrastructure identities remain in deployment secret injection: `BID_DATABASE_URL`, migration and proposal-specific database connections, `BID_ENCRYPTION_KEY` and retired keys, `BID_TOKEN_KEY`, `BID_SECRETS_KEY` and retired keys, platform TOTP seeds, bootstrap passwords, S3/MinIO credentials, and sandbox mTLS private keys. Although S3 and sandbox identities do not unlock the database, they serve recovery, startup, and both ends' identity configuration and are excluded initially. Administrator lists, endpoints, bucket names, model names, and nonsecret runtime settings keep their existing channels. URL userinfo, query-string tokens, and extra authorization headers must not reintroduce provider secrets.
- Reuse BYOK's independent Fernet domain `BID_SECRETS_KEY`, separate from data/signing keys and all retired root keys. The authenticated encrypted JSON envelope includes version, `domain=platform_credential`, row UUID, immutable name, purpose, provider, normalized endpoint, secret_version, and api_key. Compare every field against the row after decryption. Copying ciphertext across rows, renaming, changing endpoints, or using it across the BYOK domain must fail. The envelope is a Fernet-encrypted structured payload, without an additional per-row DEK/KMS wrapping layer.
- Distinguish two rotations: console “替换密钥” replaces the row's ciphertext and increments secret_version/revision. Root-key rotation extends `app.admin rotate-encryption` with provider-secrets scope and the decrypt-only `BID_SECRETS_KEY_PREVIOUS` keyring, re-encrypting platform credentials and all BYOK historical revisions. The existing data-domain command cannot directly rotate credentials. Re-encryption preserves credential values, business revisions, and job identities. BYOK append-only restrictions permit only a dedicated ciphertext-rewrapping path for the migration owner, never runtime updates. Rotation is resumable and count-verifiable; bad ciphertext must fail explicitly. Retain old keys until online-data and backup-recovery requirements are satisfied.
- Only a valid platform session issued through existing platform login, password, and TOTP may list, create, replace, enable/disable, remove, or test credentials. Reuse [ADR 0001](0001-platform-console-access.md) session lifetime and deployment administrator allowlist. Org users, org sessions, and API tokens cannot manage or read credentials; there is no token-grantable platform credential scope. API/CLI/pages never return full keys, including creation responses; expose only fingerprints and last four characters. Write-only applies to every human/client interface; necessary decryption occurs briefly in trusted service-call memory.
- Reuse the restricted function-owner pattern of `bid_platform_fn`, without extending that role's access to new ciphertext. New `bid_platform_credentials_fn` is `NOLOGIN NOSUPERUSER NOBYPASSRLS` and has only table permissions required by fixed credential functions, with no org business-table privileges. Org runtime role `bid_app` has neither direct table access nor these functions' EXECUTE or role membership. The dedicated platform management connection executes only metadata and write functions; the dedicated API/worker resolver connection executes only a single bound-ciphertext function for a verified consumer. Neither gets table SELECT/UPDATE, inherits the owner, or has `BYPASSRLS`. Functions fix `search_path`, fully qualify objects, revoke PUBLIC EXECUTE, and prohibit dynamic SQL. TOTP is verified at the platform application boundary; forgeable `SET app.*` is not authentication. Separate connection roles isolate org SQL paths, not an entire compromised service process holding root keys.
- Successful changes and appends to `platform_audit_logs` share one transaction. Tests persist a start event before recording allowlisted results. Administrative metadata reads also record access; rejection, conflict, rotation, and import record bounded classifications. Never record request bodies, ciphertext, plaintext, Authorization, remote responses, arbitrary provider errors, or operator-entered free text. Audit is not UPDATE/DELETE-capable; failures must not appear saved or successfully tested.
- Org jobs still fix BYOK revisions or catalog identities under the [existing provider configuration contract](../notes/provider-config.md#resolution-and-cache). Platform identities fix only credential references. Before every real outbound call and every retry, API/worker reads committed credential state and decrypts the latest secret_version. Initially, no ciphertext, plaintext, or “available” verdict is cached across calls; pools reuse only connections without authorization headers. Replacement affects the next resolution; disable/remove or database failure makes the next resolution fail, with no environment, old-key, alternate-model, or search fallback. A call already resolved and started is in flight and cannot be promised withdrawn; emergency revocation also requires vendor revocation of the old key.
- Removal uses a tombstone: erase online ciphertext, retain row identity/audit, and never reuse name. Catalog entries and queued jobs still referencing it are explicitly unavailable. Replacing a key preserves catalog version, prices, and model-result cache keys; changing catalog credential references still uses catalog revision checks. Returning a completed cached result performs no outbound call and does not reuse a key.
- Provide explicit, one-time protected import. After cutover, API, worker, and standalone/eval refuse startup if legacy provider-key environment variables or direct configured values in scope are present; do not silently ignore them. This exposes old deployments and missed callers instead of letting old processes use environment keys after the console reports disabled.

## Tradeoffs and consequences

A global table provides one maintenance entry point for shared vendor accounts and requires an explicit permission exception. Two restricted pools and a function owner add deployment work, but application checks on shared `bid_app` connections cannot prove the org database role cannot read platform ciphertext. Back up and protect database and root keys separately: a database leak alone cannot decrypt, but this design cannot protect simultaneous database/root-key compromise.

An extra database read per call provides a defined replacement/disable boundary and avoids resurrecting old keys through TTLs or missed invalidation notifications. Database failures stop new paid requests. Old online values are not retained: a mistaken replacement requires resubmitting a valid key, with no one-click recovery. Backups may retain old ciphertext; removal is neither vendor revocation nor cryptographic erasure from backups.

Connection tests default to allowlisted authentication-metadata probes, without model generation, org material, or billed search. Adapters without such a probe return `unsupported`. Probes do not prove inference capability, balance, or model authorization. Metering for paid synthetic calls is defined by the [decisions](../plan/platform-credentials.md#decisions); credential testing cannot add anonymous global UsageRecord entries or bypass org isolation.
