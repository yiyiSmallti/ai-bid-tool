# Draft contract: functional screenshots, prototypes and vendor evidence images

Status: **Partially implemented: Phase A, export integration, prototype generation, vendor web/PDF capture and vendor search; local browser capture not implemented**. The approved scope and recommended decisions remain effective; see the [Phase A implementation record](#phase-a-implementation-record) for implementation boundaries. Covers [roadmap](roadmap.md) B06/B04 and the B05 cropping, region-box and watermark boundaries. This contract follows the approved recommended options; see [Decisions](#decisions).

## Goals and boundaries

Capture a running UI, collect vendor (厂家) materials, or generate an HTML prototype (原型) → local redaction (遮挡) and human inspection → archive within the org (organization/tenant, 单位) → multimodal matching, text reading and region suggestions → link to a response card (响应卡) for a fixed requirement → a person in the corresponding review domain (职责) checks the image and response (响应) → confirmed materials enter the draft (初稿) → decide, item by item, whether to retain or replace prototypes before final export.
The goal is to explain, for each image, which function it supports and to what extent; image count does not establish response completeness.

The product input is a 663-page winning bid (标书) described by the product owner: a bid letter and authorization forms, a substantive response summary, commercial (商务) and technical (技术) deviation (偏离) tables, approximately 217 screenshots or diagrams across approximately 305 pages of itemized technical responses, approximately 125 pages of full-page scans, performance contracts and award notices, team social insurance and certificates (证书), a 164-page technical solution, and page-by-page seals applied in a government electronic bidding client. These are requirements background, not materials verified for this draft or fixed page quotas. Images, full-page supporting materials and long solutions must retain distinct sources and purposes and cannot impersonate one another.

This slice accepts software screenshots, existing diagrams, fixed certificate PDF pages, vendor web pages/white papers obtained through search, and single-page HTML prototypes generated by an LLM for individual functional requirements. HTML is rendered and captured in the sandbox defined by the separately developed `docs/plan/sandbox.md` draft; this document defines only inputs, artifact relationships and evidence (证据) consumption, not the sandbox's execution, security, network or resource contract. Approval and interface integration of that draft are implementation dependencies for prototype rendering; ordinary browser execution of generated HTML is not a substitute.

Prototypes may serve as Evidence in response cards and drafts just like real screenshots. Bidding and project development may proceed in parallel, and a generated prototype may become the delivered frontend, so images, drafts and exported documents carry no watermarks or visible prototype labels; source, generation model and HTML hash are retained internally. Multimodal assistance uses GLM and DeepSeek whose image-input capabilities have been verified in the platform catalog, through the existing provider layer, to match requirements, suggest regions and read image text; it does not replace human verification. This document does not duplicate specific development-catalog models, prices or credentials, or reopen whether these two model families can read images.

Entrypoints are the API and local/remote CLI. Image archiving, Evidence and draft may be completed first; Word layout remains B11, but delivery after approval of this draft must include image consumption, prototype-decision gates and actual-file acceptance integrated with the [approved export contract](export.md). Full acceptance cannot be claimed before export integration.

Hard boundaries come from [agent.md](../../agent.md#hard-rules-must-never-be-violated) and the [design document](../design.md#processing-flow-and-cli-inventory). Response review domains, card states, item-by-item confirmation, deviations and draft coverage follow approved [ADR 0005](../adr/0005-human-confirmed-responses.md), implemented as described in [response-cards.md](../notes/response-cards.md). The prototype exception below is an approved rule amendment; per-card confirmation, domain responsibilities, the token prohibition on confirmation/export, and org isolation continue to apply.

### Effective rule amendments

These amendments took effect with approval of this contract and have been synchronized to agent.md, the design document and export.md; this section retains their rationale.

The approved amendment replaced the former requirement in [agent.md rule 3](../../agent.md#hard-rules-must-never-be-violated) that screenshots generated by `ui mock` for unimplemented functions must bear a “设计原型” watermark with the following:

> `ui mock` may generate single-page HTML from functional requirements and render screenshots in the sandbox specified by docs/plan/sandbox.md. Prototype images carry no watermark; images, drafts and exported documents carry no visible prototype label. A prototype may serve as Evidence after existing per-card human confirmation (人工确认); the system must internally retain origin=prototype, generation model and HTML hash. Before final export, a person with the corresponding review domain must explicitly select “保留：它已是或将成为交付界面” or “替换为真实截图” for every Evidence item referencing a prototype; module-level batch decisions are allowed with an item-by-item trail. Undecided items or incomplete replacements block final export but do not independently block a review copy (审阅件). This decision cannot replace evidence confirmation or human export authorization. Generating vendor pages, reports or certificates remains prohibited; hardware evidence still comes only from real web pages or files.

This exception also replaces the corresponding former visible-prototype-label constraint in the [design document](../design.md#security-and-compliance), and adjusts the scope of ADR 0005's material-authenticity constraint for functional prototypes only. It does not extend to hardware parameters, test reports, certificates or other supporting materials. Feature status remains its existing declaration; prototype confirmation does not automatically make it implemented, and a retention decision is not system certification of delivery.

The approved rejection list for the [export.md export gates](export.md#export-gates-and-document-content) applies to preflight, prepare, worker input loading/saving, release and download rechecks:

| Prototype Evidence state | `final_section` | `review_copy` |
| --- | --- | --- |
| Evidence confirmed by its review domain; retention/replacement undecided | Reject with `prototype_decision_required`; acknowledge cannot bypass it | May consume the confirmed image; an incomplete decision is not itself a rejection |
| Valid `keep`, explicitly stating it is or will become the delivered UI | Allow if all other export gates pass | Allow |
| `replace` selected, not yet replaced by a confirmed real screenshot | Reject with `prototype_replacement_pending` | Allow the still-valid confirmed old prototype; a reopened card follows existing stale/gap gates |
| Bound Evidence/card revision/image/HTML hash or selection changed | Reject with `prototype_decision_stale`; decide again | A stale prototype decision alone does not block; invalid materials/cards still fail existing gates |

Unconfirmed Evidence, stale drafts, invalid citations, damaged files and unauthorized access remain rejected in both modes under export.md. Review copies retain document-wide markers such as “审阅件·不得提交” and completion code 5, with no text identifying prototype origin. Prototype-gate reasons appear only in internal preflight/review workspaces, not in draft body text, attachment titles, images, captions, alt text or exported documents. Prototype decisions are fixed as a separate internal manifest and do not become draft gaps (缺口).

## Capture, provenance and hashes

Every archived object retains separate source information and a reviewable image; derived images do not overwrite sources:

- Common metadata: org, task, explicit extraction job, material type, provider and actor kind, receipt time, fixed selection/revision, source-byte SHA-256, source dimensions, processing-plan hash and tool/profile version. The server records `received_at`; source-event time is separate. All times are timezone-aware and output in UTC.
- User screenshots/diagrams: retain sanitized source label, software/diagram version, environment, declared time and optional `captured_at`. Unknown time is null; without the original file, do not invent an original-image hash. Client-provided source hashes are `client_declared`; the server guarantees only the hash of bytes actually received.
- Browser: locally generate `capture_id`, actual capture time, BrowserProvider/browser version, viewport, device scale factor, capture mode and original pixel dimensions; retain credential-free system origin and a human-inspected route label, not full query strings, fragments, user information, DOM, HAR or page body text. This receipt is a local capture record, not a third-party trusted timestamp or tamper-resistant remote attestation.
- Certificate page: the server resolves original PDF hash, fixed original-file ID, page, 150 dpi, rendering profile/time and full-page PNG hash from an authorized Archive; clients cannot replace these values. Rendering time is not certificate issuance time.
- Vendor source: record requested/final URL, `captured_at`, page/PDF title, media type, exact product selection/revision, `content_sha256`, `archive_sha256` and archive-copy descriptor. PDFs also have page, page count, rendering profile and page-image hash. Web archives include same-capture page content and a static-dependency manifest; PDF archives fix file bytes. Do not screenshot and then download another version as the same source. URLs retain only what public-source location requires; reject credentials, temporary signatures or personal data, and do not copy URLs/page text into logs.
- Prototype: internally retain `origin=prototype`, generation job, provider, actual response model/catalog revision, prompt/schema/adapter versions, redacted-input hash, `html_sha256`, HTML archive descriptor, sandbox rendering receipt ID/hash and screenshot-source hash. Recognize only the fixed HTML artifact's relationship to that receipt; HTML hashes are not PNG hashes. Generation retries, HTML changes and re-rendering must retain new artifact relationships rather than overwrite old evidence sources.
- Distinguish at least `source_sha256` (source before processing), `upload_sha256` (redacted image actually received), `image_sha256` (final server-normalized/annotated PNG) and `plan_sha256`. Never interchange them. `source_hash_assurance=server_verified` applies only to source bytes the server can actually read and revalidate. A locally captured web archive with a verifiable upload hash does not become proof of a live page witnessed by the server.

File hashes cover actual bytes; plan hashes cover validated UTF-8 JSON with explicit defaults: sorted keys, no extra whitespace, ensure_ascii=true, no trailing newline, and preserved rectangle-list order. Metadata digests are separate; do not create circular dependencies between file hashes, source hashes printed in watermarks and final image hashes. Hashes establish byte identity, not authentic capture content or requirement satisfaction.

Browsers capturing running systems execute on the user's machine; even in remote API mode the CLI does not give intranet addresses to SaaS workers. Connect only to explicitly specified sessions/pages authorized by the local user; expose no public debugging port, do not enumerate existing tabs automatically, and do not upload browser profiles, Cookies, passwords, Authorization or storage state. Capture only: no login, business-form submission or business-data changes. Timeout, login pages or mismatched targets fail explicitly rather than pass off error pages as target functions. Real addresses enter through private configuration and are not echoed in logs; trace/video/HAR and screenshot persistence are disabled by default.

Vendor search uses SearchProvider and sends only the fixed vendor/model and text-redacted parameter keywords, never entire tender documents (招标文件) or images. Results are URL candidates for verification; after human selection the local public-page/PDF capture entrypoint downloads, archives and captures them without customer login sessions. Support only public HTTP(S) sources, validate each address hop, and reject non-web protocols, local/private/metadata addresses, credentialed login and unapproved redirects. Error pages, search summaries or a different model in the same series cannot replace selected-product materials. Vendor ownership, model/version and page applicability must be checked in per-card review.

Archives and screenshots both undergo local privacy inspection. With no required public-source redaction, content hashes may match; if a copy must remove sensitive content, retain separate captured-content and actual-redacted-archive hashes plus processing version/plan. Do not call the redacted copy a byte original or store an additional unredacted copy. Redacted parameters cannot be reconstructed from the original web page or model inference. Web archives serve only internal verification and run no scripts in authorized previews; exports use confirmed images only, never active web pages.

## Privacy: process pixels before persistence

The recommendation is local preprocessing followed by human release for ingestion; this is separate from per-card evidence confirmation. Quoted prices, contacts, identity-card numbers, bank accounts, social-insurance details, student/employee personal information, accounts/session credentials and similar data must be processed before any new persistent file or upload. Originals come from callers' existing files or browser memory; this slice stores no extra unredacted copy.

1. `prepare/capture` decodes in bounded memory and local Rust subprocess pipes, applies opaque solid-color redaction, normalizes orientation/format and strips EXIF/PNG text metadata before writing a new redacted PNG and receipt. Blur, transparency, removable layers or DOM-only masking cannot substitute for pixel destruction. Never persist redacted values, recognized text, DOM or pre-redaction thumbnails. Fail directly if Rust lacks the required privacy profile.
2. A local user views the actual redacted image, then submits the exact `reviewed_upload_sha256` and plan through a human login session. The API recomputes the received-byte hash and rejects mismatch. Callers may submit several images sequentially after individual privacy inspections; “confirm all evidence” is no substitute. Even with no sensitive regions, explicit inspection is required; an empty redaction list is not automatic approval.
3. The server limits body/decoded size; upload streams must not reach disk through framework temporary files, proxy body caching or debug dumps. It normalizes encoding by source profile, then stores encrypted content. Prototypes have no watermark/footer; other sources follow the next section's annotations. Human inspection binds upload and derived-final hashes. Do not send original sensitive data to a cloud model to check for omissions. Automated detection may suggest only; it cannot prove completeness, nor can a client declaration prove sufficient upload redaction to the server.
4. Existing certificate originals and EvidenceSource remain separate unchanged archives. Authorized reads derive redacted images in memory without copying unredacted originals into this slice. Original-file read permissions remain independently effective; this step cannot claim historical PDFs were redacted or deleted. Image-evidence previews provide only the new redacted derivatives.
5. On discovering an omission, withdraw the asset first and immediately block new previews, confirmations, draft consumption and future exports, retaining audit and historical references. Additional redaction creates a new image/Evidence requiring review again. Old downloads cannot be remotely recalled; historical-sensitive-object retention, permanent deletion and backup cleanup require a separately approved retention policy, not overwriting old images to pretend erasure.

New human-only scope `screenshot:ingest` records privacy inspection of the uploaded image, granted only to valid admin/bidder/technical sessions; token/agent/worker cannot obtain or act through it. Restricted agents may prepare local candidates, annotate regions on redacted assets and edit unconfirmed cards. Privacy release does not fill `Evidence.confirmed_by` or authorize response confirmation/export. Services and database both enforce this boundary.

[Model outbound redaction](../notes/model-drafting-redaction.md#outbound-rules) handles model text copies; this draft handles pixels before storage. They cannot substitute for one another. Disabling task `model_redaction_enabled` does not disable image-redaction requirements. New explicit multimodal operations send only locally redacted derivatives released by a person, not originals, original PDFs, web archives, HTML, Cookies or signed download URLs; the server rechecks exact outbound image hashes. Existing text-only card generate does not implicitly send images or expand material scope.

Prototype HTML generation reads only allowlisted redacted text from fixed requirements and feature selections, without real personal/quote data. Generated content also undergoes inspection before archive/screenshot ingestion. Sandbox artifact handoff and temporary lifecycle follow sandbox.md; after screenshot handoff, local pixel redaction and human ingestion gates are mandatory. Generation workers cannot supply privacy release.

### Multimodal assistance contract

Explicit `screenshot analyze` fixes requirement ID/citation hash, image rendition/hash, pixel mapping, task material selection, model catalog identity/price, reasoning level, redaction version and input manifest. Optional purposes are `match_requirements`, `propose_regions` and `read_text`, all in this slice without requiring separate cloud OCR. Platform configuration selects image-capable GLM or DeepSeek; unsupported endpoint formats are explicitly rejected rather than silently switching models, uploading originals or returning an automatically affirmative fallback.

The model sees only explicitly selected requirements' redacted text and derived images. Each image uses a request-local ref mapped by the server to an internal ID; models cannot return URLs/storage paths to establish sources. Outputs are match candidates, region rectangles and text-reading suggestions, optionally with confidence/uncertainty reasons. No match may produce an empty set; do not auto-generate evidence to fill coverage. Coordinates must fall inside the actual outbound image's content region and map back through a fixed transformation; reject excess, out-of-bounds or unknown refs. Model-read text is not a verified verbatim citation and cannot directly populate old quote fields or upgrade `human_image_review`.

Suggestions enter immutable unreviewed records only. A person must view the corresponding pixels and correct observation text before linking to cards and confirming under the review domain. Programs may apply candidates to editable cards but cannot overwrite pending_review, confirmed, comply_only or recorded negative deviation (负偏离). Model generation, suggestion adoption, privacy release, evidence confirmation and prototype export decisions each retain a trail; none replaces the next gate. All sent materials conservatively become dependencies, even when the model ultimately cites none.

## Cropping, region annotations and unlabeled prototypes

Coordinates use orientation-normalized source pixels with top-left origin; integer rectangles require `x/y >= 0` and `width/height >= 1`. Redact first, crop second, draw boxes third, and add a fixed source footer last for non-prototypes. Cropping/boxes must not redraw text, parameters, times, certificate numbers or seals, or reconstruct redacted areas. Diagrams cannot become screenshots; internal prototype provenance is inherited and cannot become a real source through cropping, reading, confirmation or keep.

Initial processing stores source-coordinate redactions/crop/boxes. Later derivations read only the redacted parent's content region, with all coordinates relative to it and no footer/padding references. Every box must fit completely inside the crop; out-of-bounds fails directly. Retain parent-image ID, processing plan, `content_offset_x/y`, content width/height and footer height. Successive mappings lead back to source positions, distinguishing redacted positions from tool-generated areas. One image may yield different regions and one derivative may support multiple cards, but each card has separate Evidence and human judgment.

Use [annotation.md's exact pixel rules](annotation.md#exact-input-and-pixel-decisions-confirmed-with-approval) as the Rust rendering basis: no automatic resizing, 2 px red inner-border boxes, RGB PNG without alpha, fixed encoding. Source/output maximum side is 8192 px, maximum pixels 20000000 and maximum PNG 40 MiB; configurations may only lower these limits. Local PNG/JPEG ingestion has the same byte/pixel limits; reject SVG, HTML, animation, excessive decoding and arbitrary path references. Generated HTML follows the separate prototype sandbox contract and cannot execute as image-upload content. At most 20 boxes and 200 redaction rectangles per operation; reject post-footer overflow without silent downsampling.

Non-prototypes use `screenshot-markup-v1` with fixed footer source type/hash, source-time nature, plan hash and “已脱敏” marker; do not call derivatives originals or claim verified authenticity. Certificate pages still show fixed source ID/page. Confirmation appears in authorized views without rewriting archived PNGs. Chinese watermark fonts are fixed in the build with verifiable licenses, never downloaded at runtime.

Prototypes use `prototype-clean-v1`: all source-image handoff results, uploaded archives, previews, thumbnails, local outputs, crops and later derivatives carry no watermark/footer/visible prototype label, with `footer_height=0`. Draft/export use only neutral attachment numbers, requirement references and necessary hashes, without prototype nature, model names or “设计原型” text. Internal details/human decision UIs provide full provenance. Generation prompts must not insert such HTML labels; labeled artifacts require regeneration/revised HTML and sandbox rendering rather than erased pixels disguised as repair. This is not a general watermark-removal feature and cannot alter/remove original certificate/vendor-file markings.

## Gates for images to become response evidence

1. After human privacy release, assets remain `unconfirmed_material`, `confirmed_by=null`, and never independently qualify for draft/export. Generating an image or obtaining a short signed preview does not establish Evidence.
2. `card create/update` adds discriminated `image_region` input referencing exact asset, derivative/final hash, visible region, `claim_scope` and human-written observation. Require the same org/task/extraction job and still-valid feature/product/certificate selection. The server resolves fixed revisions, sources and descriptors, accepting no arbitrary URLs/paths. Across cards, independently check every requirement without reusing another card's confirmation.
3. Region descriptions are observations, not verbatim excerpts. The new branch uses `visual_observation`, never old `quote` or fabricated `exact_field_match`. Certificate pages lacking text may use image-based per-image human review; old `certificate_pdf_page` still requires exact source-text matching, unaffected by the image branch.
4. Image kind must match purpose: `functional_observation` accepts known-environment running/development screenshots and fully sourced prototypes to describe functional UIs. Prototypes may establish image_region Evidence with the same standing as real screenshots and are not rejected for planned/developing status. This does not automatically prove deployment or completed workflows. `document_excerpt` accepts fixed certificate pages, `hardware_documentation` archived real vendor web/PDF, and `design_explanation` existing diagrams. Prototypes cannot prove hardware parameters/reports/certificates. Reviewers still judge whether a clause explicitly requires an actual system, performance result or full original and truthfully retain deviations.
5. Humans use existing `card confirm`, submitting expected card revision and `reviewed_evidence_ids` exactly covering all links, and handle source declarations, test environments, crop/redaction and material-obligation warnings. Evidence fixes its final image hash at creation; replacing image/region creates new Evidence/card revision. The responsible person must open that exact image version and check source, feature version, image, observation and negative deviation item by item. The server rechecks file hash, privacy release, non-withdrawal, fixed selection/current permissions, then confirms Evidence/Card in one transaction.
6. Unconfirmed, withdrawn, hash-mismatched or source/selection-invalid images cannot enter response rows or attachment manifests. Gaps contain only requirements/reasons without candidate images. Draft fixes image ID/hash/region/plan and Evidence confirmation metadata, not permanent URLs; old-draft reads recompute validity. Export rechecks the same conditions, takes only reviewed redacted images and cannot substitute unredacted originals or the latest image.

Domain permissions, human per-card confirmation, reopening and API-token prohibitions on confirmation/export remain unchanged. Ingestion permission does not give admin cross-domain confirmation rights. One screenshot supports only its observable state, not automatically an entire workflow, authenticity, performance or customer-site delivery. Redacted/cropped essential proof is unobservable: request suitable materials or record insufficiency truthfully without secretly restoring it from originals.

### Prototype decisions before final export

This gate determines whether prototypes stay in final documents as delivery UI, without reconfirming card content. The recommendation assigns decisions to the card's domain owner, usually technical for software; bidder still performs human release under export.md. Writes require a valid human session, reusing `evidence:confirm` and domain checks, never token/agent/worker or automatic admin entitlement. Every prototype Evidence starts `undecided`; this does not stop confirmed Evidence entering draft/review_copy or automatically make the draft partial.

- `keep` explicitly selects `already_delivered` or `will_deliver`, meaning “它已是或将成为交付界面”. One valid decision suffices per fixed Evidence, without repeated decisions for every export. Retain internal origin=prototype/model/HTML hash; retention is neither source conversion nor delivery certification.
- `replace` requires a real screenshot; clicking alone does not remove final-export blocks. The owner reopens the card, links new real-screenshot Evidence, reviews/confirms per card and reassembles tables. Replacement completes only when the service verifies that response no longer uses the old prototype. A new prototype requires its own retention/replacement decision.
- Module-level batches first preflight to return module label, fixed feature-selection set, each Evidence/card revision/rendition/image/HTML hash and set digest. Existing Feature has no module entity; first-version modules are labels for explicitly selected feature groups, not vague names or all current items as authorization. Every item must belong to the listed set. A person may select keep/replace for a module or item by item; submissions expand to complete item lists. The whole batch validates/commits atomically; one unauthorized, omitted, duplicate or changed item fails all. Module decisions do not confirm other cards.
- Decisions are append-only versions; changes require a reason and expected previous decision ID, initially null. Request retries are idempotent, checked under task/card locks. Changed Evidence/region/final image/HTML/card revision/task selection invalidates reuse. New references require new decisions; selecting old resources again does not revive old decisions.

Final export's internal input manifest includes each decision ID/version, exact bindings and decision-set hash, recomputed at all stages. Ordinary acknowledge_issue_ids, `--force`, privacy release, card confirmation and release cannot create keep. Decision changes invalidate dependent final runs/candidates/exports and require prepare/release again under export.md; downloaded copies cannot be remotely recalled. Review copies do not depend on decision sets or become invalid merely from keep/replace changes, but retain existing gates for reopened cards, withdrawn images and similar changes.

Approved B11 attachment consumption extends to this draft's image_region: consume only fixed derivatives from confirmed Evidence, retain exact PNG hashes and existing appendix/numbering layout, without regeneration, live capture or outbound calls. Image deduplication cannot discard per-Evidence decisions; every requirement citing the same prototype needs its own valid decision. Undecided/incomplete-replace items appear only in final-export gate reports, never printable prototype labels.

No screenshot-specific card state machine or tenant-bypassing global gallery. Files are reused only within one org/task/fixed-source relationship; associating identical bytes with another feature requires a separate asset, never cross-tenant hash deduplication.

All business references use org_id composite foreign keys plus same-task/parent constraints:

- asset → `(org_id, task_id, extraction_job_id)` with successful extraction job and same-task document; feature branch → fixed `(org_id, task_id, task_feature_id, feature_revision_id)` and its product; certificate branch → Archive's same-task source/selection/revision/file/page combination. JSON IDs alone are insufficient.
- Vendor archive/candidate/run → same `(org_id, task_id, extraction_job_id)` and `(org_id, task_id, task_resource_id, product_revision_id)`; PDF page images also bind archive/page. Prototype run → same-task requirement/extraction job/feature selection/revision/generation_job, without mixing another feature's HTML. External prototypes lacking model/HTML records cannot impersonate generation runs.
- rendition → `(org_id, task_id, asset_id)`; parents must share the asset and reference existing records, preventing cycles/cross-asset rebinding. review/withdrawal → same asset; review rendition/hash matches actual ingestion. Human references use `(org_id, memberships.user_id)` and tokens use org composite keys.
- Reuse `evidence`, `card_evidence_links`: proposed Evidence additions are screenshot_asset/rendition composite references, `visual_observation`, region, purpose and fixed image SHA, linked to exact card revision. Only image_region may have null quote; old branches retain nonempty verbatim quote. Add material kinds `user_screenshot/browser_screenshot/user_diagram/certificate_image/vendor_web/vendor_pdf/prototype`.
- analysis inputs/suggestions → same-org/task run/requirement/rendition/asset chain; model free refs are not foreign keys. Decision items → same batch/org/task/job, Evidence/card_revision/image/HTML/feature chain and prior decision, with composite unique keys rejecting same-org cross-task/card combinations. Human references remain `(org_id, memberships.user_id)`; services/DB also check domain/current revision.
- Extend table-assembly (组表) input manifests to fix image dependencies/withdrawal status. Job document_id still references this extraction job's actual tender Document, never fabricated tender documents or certificate IDs to satisfy non-null.
- Add prototype decision associations in export_run_evidence including org/run/evidence; final mode requires valid keep covering all prototype Evidence, while review_copy does not. Decision IDs only in manifest JSON are insufficient without foreign keys/integrity gates. Services/DB/download rechecks cannot rely on disabled UI buttons.

SQL constraints/triggers and services jointly check mutually exclusive branches, source/image-kind matching, JSON nonemptiness/NULL, pixel limits, parent chains, human-write gates, evidence confirmation and table-assembly consumption. Runtime roles cannot UPDATE/DELETE historical assets, archives, generation/analysis records, suggestions, derivatives, privacy releases, decisions, withdrawals or audits. First Evidence confirmation follows existing controlled gates. Tokens cannot receive screenshot:ingest; prototype decisions reuse prohibited evidence:confirm with no agent-accessible human-decision scope. Lock order remains task → card → related records; render/object I/O holds no long transaction, and release rechecks in a short transaction.

Input validation and output constraints:

- prepared is a local receipt, not an approved source. The API accepts only multipart PNG and ScreenshotIngest; it obtains vendor archives from sandbox capture artifacts server-side, not uploads, and recomputes upload SHA, dimensions and plan hash. Callers cannot supply org, confirmer, permissions, storage keys, free watermark/profile or server-resolved resource revisions. Revalidate the complete certificate source relationship/hashes from Archive. A trusted server Renderer produces the final image, whose hash may differ from upload. Vendor input requires matching reviewed_archive_sha256; other branches require null. prototype_run_id resolves actual model/HTML/sandbox receipt/source image; clients cannot fill these facts.
- prepare --input is ScreenshotPrepareInput; source.kind, --file/--source and source ID must agree. capture --input is ScreenshotCaptureInput; the tool supplements actual capture receipts as BrowserSource before identical privacy processing. --config defines only local target, authorized session and necessary element locator, never arbitrary scripts, page changes or output paths; it cannot enter upload receipts.
- On receiving prepared images, locate redacted content through verified mapping, then apply the server profile: prototypes have no watermark/footer, others a fixed footer. Do not misapply source-coordinate redactions/crop to already cropped images. Store both coordinate transformations and verify output consists only of upload content and annotations permitted by the profile. Certificate branches additionally replay the same plan from fixed source in memory and compare redacted content to prevent unrelated-image impersonation. Uploaded/browser originals are absent server-side, so do not claim that check for them.
- `system_origin` accepts scheme/host/port only, never userinfo/path/query/fragment. Free labels/versions also require privacy inspection. Local tools generate BrowserSource capture fields; ordinary upload parameters cannot impersonate them. The API still declares client_declared assurance.
- VendorSource names only a page image from a successful same-task/extraction-job vendor_capture. The server resolves URL/final URL/time/title/content/archive hashes from run/proxy receipts. Web runs require `archive=bundle`; PDFs archive original bytes. Title comes from entry-page `<title>` or null, never invention. Archive length follows source profiles; Result does not copy archive text. Prototype html descriptors must be text/html with matching html_sha256; HTML is read only through authorized archive access, never directly opened as a page.
- Initial local outputs and every server derivative preserve reversible coordinate mapping; regions reference visible content only. Limit actual decoded pixels/process resources rather than trusting image declarations or post-render checks. prototype environment requires prototype type; unknown environments can only archive pending investigation and cannot confirm functional_observation. Prototype origin/profile/footer_height are fixed to prototype/prototype-clean-v1/0, without client switches.
- Add ImageEvidenceInput as a discriminated branch of existing EvidenceInput; add image views and `quote_check=unreviewed_image/human_image_review` to EvidenceView. Old resource/text-page fields/behavior remain unchanged. Do not place observations in old quote fields to fit old models.

### Provider boundary

`LocalBrowserProvider.capture(config) -> (bytes, BrowserSource)` returns memory images and sanitized capture metadata locally only. config does not enter the database or allow arbitrary scripts/CDP commands deserialized server-side. Python orchestrates restricted Rust processes for `ScreenshotRenderer.prepare(bytes, source, plan) -> (bytes, PreparedScreenshot)` and `derive(bytes, metadata, plan) -> (bytes, rendering)`; workers also use the latter. Python validates output bytes/hash/dimensions/profile/source binding.

Proposed logical provider entrypoints are `LLMProvider.generate_prototype(fixed_text, schema)` and `VisionProvider.analyze(redacted_images, requirements, purposes, schema)`. Vision reuses platform model resolution, GLM/DeepSeek HTTP adapters, official reasoning levels, structured-output validation, safe_metadata and accounted_call; no second vendor client bypasses providers/. `SearchProvider.search(redacted_query)` returns candidates; `BrowserProvider.capture_vendor` locally captures same-acquisition web archives/screenshots or renders fixed PDF pages. HTML rendering calls sandbox.md's interface and consumes only verifiable HTML/hash/rendering receipts; this document presumes no class name/execution strategy.

Rendering subprocesses have no network/shell and inherit no tokens/service keys. Inputs/outputs/errors are bounded; recommended deadline remains 20 seconds, with owned processes terminated/reaped on timeout/cancellation. Local browser capture has a separate 30-second deadline, rejecting late results. Atomically write redacted results only to new files; reject overwrite, symlinks and path-replacement races. Files are 0600, private directories 0700; failure cleans only this operation's temporary artifacts, never user originals.

Prepaid billing does not prove arbitrary image endpoints inherit text endpoints' zero-overspend guarantee.
