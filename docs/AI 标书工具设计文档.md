# AI 标书工具设计文档

Sep 30, 2026 · @yiyi · v0.2 草稿

## 背景、目标与非目标

这个工具帮投标单位读懂招标文件、查证技术参数、校验标书并预估得分，每条结论都能追溯到原文或真实来源。它以 SaaS 方式部署，多个单位共用一套服务、数据互相隔离，也能被外部 agent 通过 CLI 直接调用。

做标书重复、耗时，且一个疏漏就可能废标。目前身边的投标人员的做法是把材料丢给懂 AI 的人，手工用大模型校验和整理参数，结果难以复用，也无法核对。

**目标**

- 从招标文件中抽取全部资格要求、技术参数、评分项和 ★ 号条款，每条带原文页码
- 为硬件参数自动采集厂家官网或白皮书的截图证据，为自研软件生成功能界面截图
- 对照招标文件校验标书，找出废标和扣分风险
- 按评分标准逐项预估得分，并给出失分原因
- 用看板把以上任务串起来，人和 agent 在同一块板上协作
- 按 SaaS 规范部署：单位之间账号和数据隔离，每个单位维护自己的模板、功能清单、产品和资质资料
- CLI 是对外接口而不只是内部工具：内置 agent 和外部 agent（如 Claude Code、Codex）调用同一套命令
- 所有模型能力（LLM、视觉、OCR、搜索、向量）都通过统一接口接入，单位可以自行替换
- 分层记忆：全局、单位、用户、项目四层，让工具越用越懂这个单位

**非目标**

- 不替用户编造证明材料：硬件证据只来自真实页面或文件，查不到就如实标注
- 不对接电子投标平台，不做电子签章和加密上传
- 不做报价策略和竞争对手分析
- 不自研 OCR 和大模型，只通过接口接入现有服务

## 用户与核心场景

使用者分四类：单位管理员维护账号、资源和模型配置；投标专员管格式、资质和进度；技术负责人管参数和方案；外部 agent 通过 CLI 代替人执行重复操作。第一批用户是身边经常做标书的人。

| 场景 | 主要使用者 | 输入 | 输出 |
| --- | --- | --- | --- |
| 维护单位资源 | 单位管理员 | 标书模板、功能清单、产品、资质、公司信息 | 可在任务中选用的资源库 |
| 创建标书任务 | 投标专员 | 招标文件 + 选用的资源 | 一个带看板的任务 |
| 要求抽取 | 投标专员 | 招标文件 | 要求清单：资格、参数、评分项、★ 号条款，带页码 |
| 硬件参数响应 | 技术负责人 | 参数清单 + 产品库中的拟投型号 | 响应偏离表 + 每条参数的官网或白皮书截图 |
| 自研软件响应 | 技术负责人 | 功能要求 + 单位功能清单 | 功能响应表 + 界面截图，未实现的用模型生成的原型截图，正式导出前人工决定保留或替换 |
| 标书校验 | 投标专员 | 招标文件 + 标书初稿 | 风险清单：废标风险、扣分风险、提示 |
| 评分预估 | 投标专员 | 评分标准 + 标书初稿 | 逐项预估分、失分原因、可补强之处 |
| 外部 agent 调用 | 外部 agent | CLI 命令 + 单位签发的访问令牌 | 与人操作相同的 JSON 结果，确认动作仍留给人 |

一次典型的使用：创建任务并上传招标文件、选择模板和产品等资源 → 确认要求清单 → 查证拟投型号的参数 → 逐条确认证据 → 导出响应表 → 标书定稿后校验和预估得分。

## 总体架构

系统以服务器方式部署：网页、CLI 和内置 agent 三种入口都经过同一个 API 层，耗时工作交给后台作业，模型和外部服务统一走接入层。

&#91;embedded content: 总体架构 · 三种入口、API 层、后台作业、数据与模型接入层\]

单位隔离、权限和审计都在 API 层一处执行，所以外部 agent 和人受到同样的约束。API 层本身也直接读写 PostgreSQL，图中省略；`ui mock`、`draft`、`export` 等命令同样以后台作业运行。

## 多租户与权限

单位是最高的隔离边界：账号、文件、资源库、记忆、模型配置和用量都归属某个单位，一个单位的数据不会出现在另一个单位的查询、提示词或检索结果里。

**账号与角色**

| 角色 | 能做什么 |
| --- | --- |
| 平台管理员 | 开通单位、维护全局记忆和平台默认模型配置；看不到单位业务数据 |
| 单位管理员 | 管理本单位成员、资源库、模型和 OCR 配置、访问令牌，审批单位记忆 |
| 投标专员 | 创建任务、确认资格类卡片、导出标书 |
| 技术负责人 | 确认参数和功能类证据 |
| 只读审阅 | 查看任务和看板，可以评论 |
| 外部 agent（令牌） | 按令牌授予的权限调用 CLI；不能确认证据，不能导出 |

一个用户可以加入多个单位，每次请求都带着当前单位的上下文。

**隔离方式**

- 数据库：所有业务表带 `org_id`，用 PostgreSQL 行级安全策略按会话中的单位过滤；应用代码漏写条件也查不到别家数据
- 文件：对象存储按 `org/<org_id>/` 前缀隔离，下载链接带签名且短期有效
- 模型调用：单位配置了自己的密钥时，费用和数据政策按该单位与服务商的合同执行
- 记忆与检索：向量检索强制带单位过滤，全局记忆对单位只读
- 后台作业：每个作业带单位上下文执行，日志脱敏

**审计与用量**

- 审计日志：登录、确认、驳回、导出、配置修改、令牌签发，按单位查询
- 用量计量：按单位记录模型调用次数和 token、OCR 页数、存储量，用于配额和计费
- 配额：单位级月度预算上限，超出后新作业暂停并通知管理员
- 私有化部署：同一套代码可以只开一个单位，部署在客户自己的服务器上

## 数据模型

核心仍是"要求"和"证据"：每条要求能定位回招标文件页码，每条证据能定位回真实来源。所有业务记录都带 `org_id`，任务内的记录还带 `task_id`。结构化数据存 PostgreSQL，文件和截图存对象存储。

| 分组 | 实体 | 说明 | 关键字段 |
| --- | --- | --- | --- |
| 租户与账号 | Org | 一个单位 | 名称、套餐、月度预算 |
| 租户与账号 | User、Membership | 用户及其在各单位的角色 | 登录方式、单位、角色 |
| 租户与账号 | ApiToken | 给 CLI 和外部 agent 的访问令牌 | 所属单位、签发人、权限范围、过期时间 |
| 租户与账号 | AuditLog、UsageRecord | 审计日志和用量记录 | 操作人、动作、对象、用量、费用 |
| 单位资源 | Template | 标书模板 | Word 文件、章节结构、适用项目类型、版本 |
| 单位资源 | FeatureItem | 自研软件功能清单的一项 | 所属产品、功能描述、实现状态（已实现、开发中、规划中）、真实截图 |
| 单位资源 | Product | 常投的产品 | 厂家、精确型号（含版本）、官方规格页、白皮书 |
| 单位资源 | Certificate | 资质证书与人员证书 | 名称、编号、有效期、扫描件 |
| 单位资源 | OrgProfile | 公司基本信息与业绩 | 注册信息、业绩合同、常用表述 |
| 任务 | Task | 一个标书制作任务（即一个投标项目） | 名称、招标编号、截止时间、成员、预算 |
| 任务 | TaskResource | 任务选用的资源快照 | 资源类型、资源 id、版本号 |
| 任务 | Document、Chunk | 上传的文件及其解析结果 | 类型、内容哈希、页码、章节路径、是否经 OCR |
| 任务 | Requirement | 一条要求 | 类别、是否 ★ 号、原文、页码、结构化条件 |
| 任务 | Evidence | 一条证据 | 关联要求和产品、来源、取证时间、原文摘录、截图和哈希、结论、确认人 |
| 任务 | ResponseItem、Finding、ScoreItem | 响应表行、校验问题、评分预估 | 偏离类型、风险级别、预估分和依据 |
| 任务 | Card | 看板卡片 | 关联对象、状态、负责人、版本号 |
| 配置与记忆 | ProviderConfig | 模型和 OCR 等服务的接入配置 | 能力类型、服务商、端点、加密密钥、作用层级 |
| 配置与记忆 | Memory | 一条记忆 | 作用域、归属、内容、来源、状态、向量 |

技术参数的条件抽取成结构化字段，这样"是否满足"可以用程序比较，而不是全靠模型判断。一条要求和它的证据大致如下（省略了 `org_id` 和 `task_id`）：

```json
{
  "requirement": {
    "id": "req-031",
    "category": "tech_param",
    "starred": true,
    "text": "★ 单卡显存不低于 80GB",
    "page": 42,
    "condition": { "param": "显存", "op": ">=", "value": 80, "unit": "GB" }
  },
  "evidence": {
    "id": "ev-117",
    "requirement_id": "req-031",
    "product": { "vendor": "某厂家", "model": "某型号 SXM" },
    "source": { "type": "web", "url": "https://…", "captured_at": "2026-10-12T10:31:00+08:00" },
    "quote": "显存容量 80GB",
    "screenshot": { "path": "evidence/ev-117.png", "sha256": "…" },
    "model_matched": true,
    "verdict": "satisfied",
    "confirmed_by": null
  }
}
```

`confirmed_by` 为空的证据不能进入响应表和导出文件。

## 单位资源库与任务创建

每个单位维护自己的资源库，创建标书任务时从中挑选本次要用的资源。任务会锁定所选资源的版本，资源库之后再改也不会悄悄影响进行中的任务。

**资源库**

| 资源 | 通常由谁维护 | 在任务中的用途 |
| --- | --- | --- |
| 标书模板 | 单位管理员 | `export` 套用的 Word 模板和章节结构 |
| 功能清单 | 技术负责人 | `ui mock` 判断功能是否已实现；已实现的优先用真实截图 |
| 产品库 | 技术负责人 | `evidence fetch` 的拟投型号、官方规格页和白皮书来源 |
| 资质与人员证书 | 投标专员 | `check` 核对资质是否齐全、是否过期 |
| 公司信息与业绩 | 投标专员 | 资格响应和业绩表的填写依据 |
| 模型配置组合 | 单位管理员 | 本任务使用哪一组模型和 OCR 服务 |

每次修改资源都生成新版本，旧版本保留；资质证书在到期前提醒，提前天数由单位设置。

**创建任务**

1. 填写任务信息：名称、招标编号、截止时间、成员
2. 上传招标文件，后台开始解析
3. 选择资源：模板、产品（可按包分别选）、功能清单、资质集合、模型配置组合
4. 设定预算上限，确认后生成看板

同一件事用 CLI 来做：

```bash
bid task create --name "某单位 GPU 服务器采购" --tender tender.pdf \
  --template tpl-standard@v3 --product prod-gpu-01 --features fl-platform@v5 \
  --certs cert-set-default --providers profile-default --budget-usd 20
```

任务创建后可以追加或替换资源，每次变更记一条审计日志，并提示哪些已确认的卡片可能受影响。

## 模型与 OCR 接入层

所有外部能力都通过统一接口调用，业务代码只认接口不认厂商：换模型、换 OCR 只改配置，不改代码。

**能力接口**

| 接口 | 输入 → 输出 | 谁在用 | 可接入的实现 |
| --- | --- | --- | --- |
| LLMProvider | 消息 + JSON Schema → 结构化结果 | `req extract`、`check`、`score`、agent | 云端大模型、自部署开源模型 |
| VisionProvider | 图片 + 问题 → 判断和位置 | `evidence fetch` 核对截图里的数值 | 多模态大模型 |
| OCRProvider | 图片或扫描页 → 文本 + 坐标 | `tender parse` 处理扫描页和资质扫描件 | 云 OCR 服务、本地 OCR 引擎 |
| SearchProvider | 查询 → 网址列表 | `evidence fetch` 找官网和白皮书 | 各家搜索 API |
| EmbeddingProvider | 文本 → 向量 | 记忆检索、相似条款匹配 | 云端或本地向量模型 |
| BrowserProvider | 网址 → 截图 + 页面文本 | `evidence fetch` | 本地 Playwright、远程浏览器服务 |

**统一约定**

- 每次调用返回结果的同时，返回服务商、模型名和版本、耗时、费用；这些写入用量记录，并随结果保存，方便评测和追溯
- 失败统一转成三类：可重试、不可重试、内容被拒，对应 CLI 的退出码
- 超时、重试、限流在接入层统一处理，业务代码不重复实现

**配置层级**：平台默认 → 单位覆盖 → 任务选择的配置组合。单位可以只覆盖其中一种能力，比如只把 OCR 换成本地引擎。密钥加密存储，界面上只显示末几位。

**配置页（以 OCR 为例）**

单位管理员在"模型与服务配置"页为每种能力配置服务：

- 选择服务类型：云服务、本地引擎或关闭
- 填写端点和密钥，选择识别语言和精度档位
- 适用范围：只处理扫描页，还是所有页面都做 OCR 校对
- "测试连接"：上传一页样例，立即看到识别结果和耗时
- 保存为配置组合，供创建任务时选择

LLM、视觉、搜索、向量也用同一套页面结构，只是参数项不同。配置同样可以用 `bid provider set` 和 `bid provider test` 完成。

## 记忆系统

记忆分全局、单位、用户、项目四层，用来让工具记住"这个单位、这个人、这个项目怎么做"。记忆只影响工具怎么做，永远不能当作参数证据。

| 作用域 | 存什么 | 谁能写 | 谁能读 | 例子 |
| --- | --- | --- | --- | --- |
| 全局 | 通用的招投标知识 | 平台管理员 | 所有单位，只读 | 常见废标条款类型、参数单位换算规则 |
| 单位 | 本单位的惯例和经验 | 成员提出，单位管理员审批 | 本单位成员和 agent | 某厂家参数以白皮书为准；过去因业绩表格式被扣分 |
| 用户 | 个人偏好 | 本人 | 本人及本人发起的 agent | 校验报告只列废标风险；响应表用简洁表述 |
| 项目 | 本任务的特定信息 | 任务成员 | 本任务 | 第 2 包改投另一型号；招标方答疑修改了交货期 |

**写入**

- 显式写入：用户在看板里点"记住"，或用 `bid memory add --scope org`
- 自动提议：驳回证据、修改 agent 的结论、把校验结果标为误报时，系统生成候选记忆，人确认后才生效；单位级候选由管理员审批
- 项目记忆：任务中的决定（选型、答疑、分工）记入项目层，任务归档后只读保留
- 不写入：报价、身份证号、银行账号等敏感数据；证据本身走证据链，不进记忆

**读取**

- 每次 agent 或命令运行前，按项目、用户、单位、全局的顺序检索相关记忆，按相关度取前若干条放入上下文
- 记忆分两类，冲突时各自有优先级：事实与规则类按项目 > 单位 > 全局；偏好类按用户 > 单位默认。个人偏好不能覆盖单位的合规规则
- 每个结果都记录用到了哪些记忆，看板上可以展开查看，并直接停用其中一条

**隔离与管理**

- 单位记忆永远不会进入全局层，全局层只由平台管理员维护
- 每条记忆带状态（候选、生效、停用）、来源（哪个任务、哪张卡片）、创建人和可选的失效时间
- "记忆管理"页按作用域查看、搜索、编辑和停用；CLI 对应 `bid memory list`、`add`、`disable`
- 存储：记忆表加 pgvector 向量列，检索时强制带单位和作用域过滤

## 处理流程与 CLI 清单

业务流程由 8 个命令组成，另有一组管理类命令。命令统一以 `bid` 为入口，在服务器上以后台作业方式执行，互不调用，可以单独重跑。

**业务命令**

| 顺序 | 命令 | 做什么 | 读取 | 写入 | 语言 |
| --- | --- | --- | --- | --- | --- |
| 1 | `bid tender parse` | 把 PDF 和 Word 解析成带页码的段落和表格，扫描页交给 OCR | Document | Chunk | Python |
| 2 | `bid req extract` | 抽取要求并结构化技术参数条件 | Chunk、记忆 | Requirement | Python |
| 3 | `bid evidence fetch` | 按产品库中的型号查证，网页截图或 PDF 区域渲染 | Requirement、Product | Evidence（未确认） | Python |
| 4 | `bid evidence stamp` | 裁剪、框出关键数值、加来源和时间水印、计算哈希 | Evidence | Evidence（已标注） | Rust |
| 5 | `bid ui mock` | 对照功能清单，已实现的用真实截图，未实现的由模型生成 HTML 原型并在沙盒中截图 | Requirement、FeatureItem | Evidence（界面） | Python |
| 6 | `bid draft` | 用已确认的证据生成响应偏离表 | Requirement、Evidence | ResponseItem | Python |
| 7 | `bid check` ∕ `bid score` | 对照招标文件校验标书；按评分标准预估得分 | Requirement、标书、资质库、记忆 | Finding、ScoreItem | Python |
| 8 | `bid export` | 套单位模板导出 Word，含响应表和证据附件 | ResponseItem、Evidence、Template | Word 文件 | Python |

**管理命令**

| 命令 | 做什么 |
| --- | --- |
| `bid login` ∕ `bid org use` | 登录服务器、切换当前单位 |
| `bid token create` | 签发给外部 agent 的令牌，指定权限范围和有效期 |
| `bid task create` ∕ `list` | 创建任务并选择资源、查看任务 |
| `bid resource <类型> list` ∕ `add` ∕ `update` | 维护模板、功能清单、产品、资质和公司信息 |
| `bid provider set` ∕ `test` | 配置并测试模型和 OCR 服务 |
| `bid memory list` ∕ `add` ∕ `disable` | 管理记忆 |
| `bid job status` ∕ `wait` | 查看或等待后台作业 |
| `bid schema` | 输出全部命令的参数和输出结构（JSON Schema），供外部 agent 发现和调用 |
| `bid mcp serve` | 把同一套命令以 MCP 服务形式暴露（可选） |

步骤 4 和 5 之后、步骤 6 之前有一个人工确认关口：标注好的证据由人在看板上确认或驳回，确认后才能进入响应表。

## CLI 设计规范与外部 agent 接入

CLI 是对外接口：看板后端、内置 agent 和外部 agent 调用的是同一套命令、同一套 JSON，权限只由身份和令牌决定。

**调用形式**：`bid <对象> <动作> [--task <任务 id>] [--json] [--dry-run] [--wait]`。不做交互式提问，缺参数直接报错。

**运行模式**

- 远程模式（默认）：CLI 是服务器 API 的薄客户端，文件上传到单位的对象存储，作业在服务器上执行
- 本地模式：用于开发和离线试用，数据存本地目录，只有一个隐含单位；两种模式的命令和输出完全一致

**认证与权限**

- 人用 `bid login` 登录，得到与网页一致的角色权限
- 外部 agent 用单位管理员签发的令牌，令牌绑定单位、有效期和权限范围，如 `task:read`、`evidence:fetch`、`check:run`
- `evidence:confirm` 和 `export` 不能授予令牌：确认和导出只能由登录的人完成

**输出**：加 `--json` 时输出统一的结果结构，每条结论都带来源：

```json
{
  "ok": true,
  "command": "req extract",
  "data": { "created": 86, "starred": 7 },
  "items": [ { "id": "req-031", "source": { "doc": "tender.pdf", "page": 42 } } ],
  "warnings": [ "第 18–20 页为图片，未解析" ],
  "cost": { "llm_tokens": 152000, "usd": 0.41 },
  "duration_ms": 38200
}
```

**退出码**

| 退出码 | 含义 | 调用方怎么做 |
| --- | --- | --- |
| 0 | 成功 | 继续下一步 |
| 2 | 参数或输入有误 | 修正后重试，重试前不会自己变好 |
| 3 | 可重试的失败（超时、限流、网络） | 退避后重试 |
| 4 | 不可重试的失败（页面不存在、内容被拒） | 换来源或转人工 |
| 5 | 部分成功 | 看 `items` 里的失败项，只重做失败的部分 |

**幂等与缓存**：同样的输入（文件哈希、提示词版本、模型名）不重复调用模型，直接返回缓存结果；重跑只更新变化的记录，不覆盖已人工确认的内容。

**预估**：`--dry-run` 只报告将要处理多少条、预估成本和耗时，不写入任何数据。

**后台作业**：耗时命令立即返回作业 id，加 `--wait` 则等到完成再返回。作业状态可以用 `bid job status` 查询，看板通过 SSE 实时显示。

**外部 agent 接入**

- 发现：`bid schema` 输出所有命令的参数和输出结构，另附一份供 agent 阅读的使用说明（含典型流程和禁止事项）
- 接入方式：支持命令行的 agent（如 Claude Code、Codex）直接调用 CLI；只支持工具协议的 agent 用 `bid mcp serve` 接入
- 可追溯：外部 agent 的每次调用都记入审计日志，标明是哪个令牌做的；看板上由 agent 产生的内容有明显标记
- 兼容性：命令和输出结构带版本号，不兼容的变更升主版本，旧版本至少保留一个大版本周期

## 关键设计决策

几个决策都服务于同一个原则：宁可多一步人工确认，也不让未经核对的内容进入标书。

| 决策 | 选择 | 原因 | 代价 |
| --- | --- | --- | --- |
| 结论必须带引用 | 每条抽取结果附原文和页码 | 人能快速核对，也能自动检查引用是否存在 | 提示词和后处理更复杂 |
| 参数条件结构化 | 拆成参数名、比较符、数值、单位 | "是否满足"由程序比较，不全靠模型判断 | 单位换算和模糊表述需要兜底，换不了的转人工 |
| ★ 号条款双保险 | LLM 抽取加符号和关键词规则扫描，取并集 | 漏一条实质性条款就可能废标 | 规则会误报，需要人工过滤 |
| 型号精确匹配 | 证据必须对应产品库中含版本的精确型号 | 同系列不同版本参数不同，混用会出错 | 查证命中率会降低 |
| 人工确认关口 | 未确认的证据不能进入响应表和导出；令牌无法获得确认权限 | 证据真实性由人负责，内置和外部 agent 都不能替人拍板 | 多一步人工操作 |
| 取证即存档 | 截图、哈希、时间和来源一起保存 | 厂家页面会改版或下架，事后仍可核对 | 占用存储 |
| 原型导出前人工决定 | 原型截图不加标注，正式导出前逐项或按模块决定保留或替换为真实截图 | 投标与项目常同步进行，原型可能就是交付前端；人工决定避免未处理的原型进入正式件 | 导出前多一步人工决定 |
| CLI 作为对外接口 | 人、内置 agent、外部 agent 共用一套命令和 JSON | 一套权限、一套测试，外部 agent 开箱即用 | 命令和输出结构要严格做版本管理 |
| 统一模型接口 | LLM、视觉、OCR、搜索、向量、浏览器各自一个接口 | 单位可自选服务商或本地模型，服务商下线时换配置即可 | 只能用各家的共同能力，特有功能需要额外适配 |
| 行级租户隔离 | 共享数据库，每表带 `org_id`，PostgreSQL 行级安全策略强制过滤 | 运维成本低，应用代码漏写条件也不会串数据 | 特大客户要求独立库时需要单独部署 |
| 资源版本快照 | 任务锁定所选资源的版本 | 资源库修改不会悄悄改变进行中的任务 | 要更新资源得显式切换版本 |
| 记忆分层且经人审 | 四层作用域，自动提议的记忆要人确认才生效 | 防止错误经验被自动放大，并保证单位间不串记忆 | 积累记忆更慢 |

## 看板与 agent 设计

看板上每张卡片对应一条要求或一个校验问题，人和 agent 都只通过改卡片状态来推进工作。

&#91;embedded content: 参数卡状态 · 5 个状态，1 个人工关口\]

参数卡只有经过"待人工确认"才能到达终态；查不到证据的卡片也停在这里，由人决定补材料还是填负偏离。风险卡更简单，只有待处理、已修复、已忽略三个状态。

**看板**

- 三种卡片：参数卡（技术参数和功能要求）、资格卡（资质和资格要求）、风险卡（校验发现的问题）
- 卡片里直接展示招标原文、证据截图、来源和模型结论，确认或驳回只需一次点击
- 筛选：只看 ★ 号条款、只看待我确认、只看废标风险
- 并发：每张卡片带版本号，保存时版本对不上就提示冲突（乐观锁）；进度用 SSE 推送

**Agent**

- 工具就是上文的 CLI，每个命令对应一个工具定义，输入输出就是 CLI 的 JSON
- 职责：理解用户意图、排序和派发查证任务、处理失败重试、汇总结果
- 权限：内置 agent 以发起人的身份运行，但和外部 agent 一样不能确认证据、修改已确认的卡片或导出
- 记忆：运行前按记忆系统的规则读取相关记忆，结果里标出用到了哪些
- 可恢复：状态全在服务器上，中断后从卡片状态继续，不重做已完成的工作
- 预算：执行前汇总 `--dry-run` 的成本，超出任务预算或单位配额先问人
- 第一版 agent 直接用 Claude Code 或 Codex 加一份 CLI 说明文件，这同时也验证了外部 agent 接入；之后再用 agent SDK 实现内置 agent

## 评测方案

每次改提示词、换模型或改规则，都在固定测试集上重跑并对比下列指标。★ 号条款的召回率是硬指标，其他指标的目标待第一轮实测后再定。

| 指标 | 怎么算 | 初定目标 |
| --- | --- | --- |
| ★ 号条款召回率 | 标准答案中的 ★ 号条款被抽出的比例 | 100% |
| 要求抽取召回率与准确率 | 对照标准答案，按条匹配 | 实测后定 |
| 引用有效率 | 引用的页码里确实包含该条原文的比例 | 实测后定 |
| 参数判定准确率 | "满足 ∕ 不满足 ∕ 未找到"与人工结论一致的比例 | 实测后定 |
| 证据通过率 | 证据被人工确认而非驳回的比例 | 实测后定 |
| 风险发现率与误报率 | 对照人工标注的问题清单 | 实测后定 |
| 单份成本与耗时 | 一份招标文件从解析到校验的模型费用和总时间 | 实测后定 |

**测试集**

1. 开发阶段：从政府采购网站下载公开的硬件类招标文件，自己标注要求清单
2. 第一版可用后：征得同意后加入真实标书，用人工最终交付的结果作为标准答案
3. 看板上的每次确认和驳回都记录下来，自动变成新的测试样本

## 安全与合规

标书包含报价和客户信息，提交的证明材料一旦不实可能废标或被追责，所以保密和证据真实是两条底线。

**数据保密**

- 文件存在单位专属的对象存储路径，静态加密；下载链接带签名且短期有效
- 只选用不拿接口数据训练的模型服务，并在配置页写明各服务商的数据保留政策
- 发给模型前可选自动遮挡：报价、联系人、身份证号、银行账号
- 单位可以用自己的模型密钥或本地模型；保密要求高的单位可以私有化部署
- 服务商密钥和访问令牌加密存储，只在作业执行时解密，令牌可随时吊销
- 演示和作品集只用公开招标文件

**证据真实**

- 硬件证据只能来自真实的网页或文件截图，工具不提供任何"生成厂家页面"的能力
- 每条证据记录来源、时间、原文和哈希，导出时可选附带证据清单
- 自研软件未实现功能的界面原型不加标注，系统内部记录来源；正式导出前须由人决定保留或替换为真实截图
- 参数不满足时如实填为负偏离，工具不提供改写参数的建议

**操作记录**：每次确认、驳回、导出都记录操作人和时间，便于事后追溯。

## 技术选型

以 Python 为主，Rust 只负责证据标注这一个边界清晰的 CLI，看板用 Vue。标注"待定"的在阶段 0 选定。

| 部分 | 选型 | 说明 |
| --- | --- | --- |
| CLI 框架 | Typer | Python 命令行，自动生成帮助信息 |
| 数据结构 | Pydantic | 校验结构化输出，生成 `bid schema` 用的 JSON Schema |
| 服务端 API | FastAPI | REST 接口、SSE 进度推送，CLI 远程模式调用它 |
| 数据库 | PostgreSQL + pgvector | 行级安全策略做租户隔离，pgvector 做记忆检索 |
| 文件存储 | S3 兼容的对象存储 | 云上用云厂商服务，私有化部署用 MinIO |
| 后台作业 | Python 作业队列（待定） | 执行解析、查证、校验等耗时命令，支持重试和取消 |
| 认证 | 账号密码 + OIDC 单点登录，访问令牌带权限范围 | 大单位可接入自己的身份系统 |
| PDF 解析与渲染 | PyMuPDF | 提取文本和坐标，渲染白皮书的指定区域 |
| Word 读写 | python-docx | 解析标书，套单位模板导出 |
| 网页截图 | Playwright（BrowserProvider 的默认实现） | 渲染动态页面并截图 |
| LLM、视觉、向量、搜索、OCR | 通过接入层配置，平台默认服务待定 | 要求：结构化输出、长上下文、图片理解、不用接口数据训练 |
| 证据标注 | Rust：clap、serde、image、sha2 | 裁剪、框选、加水印、计算哈希，作为作业里调用的独立可执行文件 |
| 看板与管理页前端 | Vue 3 + Vite | 看板、资源库、模型配置、记忆管理 |
| 部署 | Docker Compose，之后可换 Kubernetes | 同一套镜像用于 SaaS 和私有化 |
| 测试与 CI | pytest、cargo test、GitHub Actions | 单元测试、租户隔离测试、评测脚本 |
